# 终端小游戏方案 A 节奏设计

## 目标

保留现有像素美术、跳跃手感和速度范围，只修正障碍物生成节奏，让小游戏作为个人网站彩蛋容易理解、容易开始，并且不会出现满屏仙人掌。

## 当前问题

当前逻辑固定每 60 帧在画布最右侧生成一个障碍。速度为 1 时，第一个障碍从 800 像素处移动到人物附近约需 12.5 秒；在它到达前已经积累约 12 个障碍，随后形成间距约 60 像素的连续队列。降低移动速度没有同步降低生成密度，因此视觉和操作压力反而更明显。

## 已确认方案

- 初始速度继续为 `1`，最高速度继续为 `2.5`。
- 第一个障碍直接出现在画布宽度约 `60%` 的位置，缩短无事件等待时间。
- 后续障碍不再按固定帧数生成，而是依据与最新障碍的水平距离生成。
- 每次间距在 `260–360` 像素之间随机选择。
- 同时存在的障碍最多为 `3` 个。
- 保留大小仙人掌随机、现有跳跃参数、碰撞判定、计分、重开和退出操作。
- 不增加难度滑块、关卡、道具或额外 UI。

## 结构

`js/site-behaviors.js` 提供纯函数节奏模型，负责计算首个障碍位置、随机间距和是否允许生成。`js/script.js` 的 Canvas 游戏循环只消费这些结果，不自行维护另一套规则。这样可以用 Node 测试直接验证方案 A，不依赖真实 Canvas。

## 验收

- 800 像素画布的首个障碍位置为约 480 像素。
- 随机值 `0`、`0.5`、`1` 分别得到 260、310、360 像素间距。
- 未达到目标间距时不生成；达到间距且障碍少于 3 个时生成；已有 3 个时不生成。
- 游戏循环不再包含 `frame % 60` 的固定生成逻辑。
- 速度、人物滚轮状态、编辑工作台与其他网站测试保持通过。
